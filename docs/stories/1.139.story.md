## Context

Camada 2 da proposta aprovada em 2026-11-16 (ver Story 1.137). A regra no código impede que o aviso de outra tentativa de pagamento desfaça uma inscrição aprovada, mas só nas rotas que passam por ela. Esta story põe a mesma regra no banco, como última barreira para qualquer caminho que escape dela, inclusive código escrito no futuro. Mesmo padrão da proteção de valores de inscrição paga (Story 1.40, `20261014120000_protect_paid_registrations.sql`).

Tamanho: **S**. **Dependências:** aplicar a migration **depois** de publicar o código da Story 1.137.

## User Story

**Como** gestor de evento,
**quero** que o banco recuse tirar uma inscrição de aprovada sem um motivo válido,
**para** que nenhum código, atual ou futuro, cancele uma inscrição paga por engano.

## Acceptance Criteria

- [x] AC1: Gatilho `BEFORE UPDATE OF payment_status` em `registrations`: uma inscrição `payment_approved` só sai de aprovada para `payment_cancelled` com `cancelled_by` preenchido (gestor, painel ou CLI), ou pelo próprio pagamento que a aprovou (mesmo `payment_id`, não nulo) para `payment_cancelled` com detalhe `refunded`/`charged_back` ou para `payment_in_review`.
- [x] AC2: Qualquer outra saída para com erro 23514 `approved_registration_status_protected: <status>` e a linha fica como estava.
- [x] AC3: Saída documentada para DBA, local à transação (`app.allow_registration_status_change = 'on'`).
- [x] AC4: Função sem `SECURITY DEFINER`, `search_path` fixo, `EXECUTE` revogado de PUBLIC, anon e authenticated; migration idempotente, sem alterar dados.
- [x] AC5: Validação em Postgres em memória (PGlite): os 18 cenários do AC1–AC3 (barrar PIX antigo, volta para pendente, recusa de outro cartão, mesmo pagamento sem estorno, `cancelled_by` em branco, estorno de outro pagamento, análise em inscrição gratuita; liberar gestor, estorno, contestação, análise, gravação que mantém aprovada, gravação sem status, pendente expirando, saída do DBA e o não vazamento dela).
- [x] AC6: Teste de contrato do arquivo.
