# Story 1.10 - Auditoria de Persistência e Isolamento por Gestor

## Status

Ready for Review

## Context

Gestores relataram conflitos ao persistir ações em eventos. Exemplos: criar um evento, atualizar a página e o evento desaparecer; dados de contas de gestores diferentes aparentando conflito.

## Acceptance Criteria

- [x] AC1: Criação de evento só atualiza a UI depois de confirmação do Supabase.
- [x] AC2: IDs de eventos, categorias e provas evitam colisão entre gestores e nomes repetidos.
- [x] AC3: Mutations de eventos exigem `organizer_id` do gestor atual.
- [x] AC4: Mutations de categorias e provas exigem o `event_id` correspondente.
- [x] AC5: A tela de admin aguarda sucesso real antes de exibir mensagens de sucesso para criação de evento, categoria, prova e cupom.
- [x] AC6: O evento selecionado no admin sincroniza com o estado persistido mais recente.
- [x] AC7: Testes de regressão cobrem persistência confirmada e isolamento por gestor.

## Scope

### In

- Auditoria e correção da camada client-side de persistência Supabase.
- Isolamento por gestor em operações administrativas.
- Regressões estáticas para os invariantes encontrados.

### Out

- RLS completa no Supabase.
- Migração para autenticação Supabase Auth.
- Painel de auditoria operacional.
