# Story 1.37 - Qualifier: Prova Travada Só com Resultado Ativo e Exclusão de Prova com Submissões

## Status

InReview

## Context

No EVENTO TEST 1 (Functional Fitness Qualifier) o gestor lançou um resultado manual na PROVA 1 e depois usou "Excluir resultado". O leaderboard ficou sem scores, mas o formulário da prova continuou travado: tipo de score (For Time), categoria e abertura bloqueados, prazo final só podendo ser estendido e o botão Excluir desabilitado.

Causa (confirmada por leitura do banco em 08/10/2026): "Excluir resultado" (`qualifier_request_resubmission`) não apaga a submissão, só a move para `awaiting_resubmission` e apaga o score. Todas as travas (trigger `qualifier_protect_workout_after_submission`, `isQualifierWorkoutLocked` e `loadQualifierWorkoutLocks`) disparam com **qualquer** linha em `score_submissions`, sem olhar o status. Como o histórico (versões e revisões) é imutável e as FKs são `RESTRICT`, não havia caminho para destravar nem para excluir a prova; só excluindo o evento inteiro.

Decisões do usuário em 08/10/2026, sobre o relatório de análise:

1. Implementar **S1** (a trava passa a valer só com resultado ativo) e **S2** (excluir prova com submissões com confirmação forte). A S3 ("reiniciar resultados" para mudanças estruturais com resultados ativos) fica fora.
2. A exclusão de prova com submissões é **exclusiva do gestor organizador** do evento.
3. Os atletas afetados são **avisados por e-mail**.

Story criada pelo orquestrador a partir da escolha explícita do usuário (a aprovação dele substitui a validação do @po nesta story).

## User Story

**Como** gestor organizador de um evento Qualifier,
**quero** corrigir a configuração de uma prova cujos resultados já foram excluídos e poder excluir uma prova que recebeu submissões, com um aviso claro do impacto,
**para que** eu tenha controle sobre as provas sem precisar excluir o evento inteiro, e os atletas sejam avisados quando precisarem enviar o resultado de novo.

## Acceptance Criteria

- [x] AC1: Uma prova de Qualifier cujas submissões estão todas em `awaiting_resubmission` não fica travada: o gestor altera tipo de score (inclusive de ou para Tempo), categoria, abertura e prazo final (antecipar ou estender). Vale para o trigger do banco, para a validação da API e para o formulário. `event_id` continua travado com qualquer submissão.
- [x] AC2: Com pelo menos uma submissão com resultado em jogo (`pending_review`, `validated`, `penalized` ou `rejected`), as regras atuais continuam: categoria e abertura travadas, prazo só estende, tipo só entre tipos numéricos e sem resultado revisado. O aviso do formulário passa a contar os resultados ativos.
- [x] AC3: Time cap, nome, código, ordem, descrição e critério de desempate continuam editáveis em qualquer situação (regressão).
- [x] AC4: O botão Excluir de uma prova de Qualifier com submissões fica habilitado e abre um modal que mostra quantas submissões e atletas serão afetados, avisa que todos os resultados da prova serão apagados permanentemente e que os atletas terão que enviar novamente, e só libera a exclusão com: confirmação marcada, justificativa preenchida (até 2.000 caracteres) e o código da prova digitado. Provas sem submissões mantêm a confirmação simples atual.
- [x] AC5: Apenas o gestor organizador do evento exclui prova com submissões (função do banco e API). Owner, judges e gestores de outros eventos recebem erro claro; gestor com acesso expirado é bloqueado.
- [x] AC6: A exclusão é atômica (`qualifier_delete_workout`): remove contestações, revisões, versões, scores e submissões da prova e a própria prova, e grava um registro em `qualifier_workout_deletions` (gestor, justificativa, quantidade e resumo das submissões removidas). A liberação do histórico imutável vale só dentro dessa transação.
- [x] AC7: Cada atleta afetado recebe um e-mail (envio em lote pelo Resend, sem desfazer a exclusão em caso de falha) informando que a prova foi removida pela organização, com o motivo, e que precisará enviar um novo resultado quando a prova for publicada de novo. A resposta da API informa quantos atletas foram avisados.
- [x] AC8: O CLI do Qualifier ganha `workout delete` chamando a mesma função do banco (Constitution, Artigo I: CLI First).
- [x] AC9: Testes de regressão estática e unitários de `workoutEdit.ts` cobrem AC1–AC8; `npm test`, `npm run lint` e `npm run typecheck` passam.

## Dev Agent Record

### Completion Notes

- Migration `20261008120000`: o trigger da prova sai cedo quando não há submissão fora de `awaiting_resubmission`; `event_id` continua travado com qualquer submissão e o DELETE direto continua proibido. As funções de imutabilidade aceitam a flag `app.qualifier_workout_purge` (além da do purge de evento). `qualifier_delete_workout` valida gestor organizador, acesso não expirado, confirmação e justificativa, trava a prova e as submissões (`FOR UPDATE`), apaga contestações → revisões → versões → scores → submissões, desliga a flag, grava `qualifier_workout_deletions` e remove a prova. Só `service_role` executa.
- `workoutEdit.ts`: `QualifierWorkoutLock` ganha `activeCount`; `isQualifierWorkoutLocked` usa resultados ativos; novos `hasQualifierWorkoutSubmissions` e `getWorkoutDeleteConfirmationText`.
- API `deleteWorkout`: prova de Qualifier com submissões vai para `deleteQualifierWorkoutWithSubmissions` (403 para quem não é o organizador, 409 quando o painel mandou a confirmação simples com travas desatualizadas, erros do banco mapeados para mensagens). Depois da exclusão, avisa os atletas por e-mail (best-effort) e devolve `submissionsRemoved`, `athletesAffected` e `athletesNotified`. Provas sem submissões seguem a exclusão simples.
- `resend.ts`: `sendQualifierWorkoutDeletedEmails` envia um e-mail por atleta via `/emails/batch` (lotes de 100), com o motivo escapado.
- Admin: botão Excluir sempre habilitado; com submissões abre o modal "Excluir prova" (contagem de atletas, aviso "Tem certeza?", checkbox, justificativa enviada aos atletas, código da prova). O aviso de trava conta resultados ativos e o campo de prazo mostra a regra quando travado. Qualquer recusa do servidor ao salvar ou excluir recarrega as travas.
- CLI: `npm run qualifier:cli -- workout delete ...` chama a mesma RPC (não envia e-mail; o painel envia).
- Verificação: `npm test` 373/373; `npm run lint` 0 erros (208 warnings, mesma linha de base); `npm run typecheck` sem erros.
- Validação da SQL em Postgres real (PGlite, em memória, fora do projeto): as 51 migrations aplicam em ordem e 34 cenários passam (cenário do EVENTO TEST 1 destravado, travas mantidas com resultado ativo, recusas de owner/outro gestor/atleta/expirado/confirmação/justificativa sem apagar nada, exclusão completa com contestação, auditoria, flag sem vazar, purge de evento com CASCADE da auditoria, privilégios). Sem a migration nova, o mesmo cenário falha com os códigos do bug (`type_change_not_allowed`, `identity_or_window_locked`, `deadline_extend_only`).
- Não verificado no navegador: o admin exige login e a migration ainda não está no Supabase remoto. `next dev` compila `/admin` (200) e a rota responde.
- **Ordem de deploy:** aplicar a migration antes de publicar o código. Com o código novo e o banco antigo, o formulário libera os campos mas o trigger antigo recusa (409 com mensagem) e a exclusão com submissões responde 503 pedindo a migration.
