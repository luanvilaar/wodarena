# Story 1.21 - Bootstrap Resiliente e Carregamento Progressivo

## Status

Ready for Review

## Context

O carregamento inicial da aplicação é bloqueado por um overlay global enquanto o `AppContext` aguarda um bootstrap amplo. Em recarregamentos com sessão persistida, a hidratação do `localStorage` pode iniciar chamadas públicas e privadas concorrentes; sessões expiradas ainda podem gerar novas chamadas públicas. O bootstrap também consulta tabelas inteiras e não possui timeout, cancelamento, estado de erro recuperável ou telemetria suficiente.

## User Story

**Como** usuário da WODArena,
**quero** que a aplicação carregue o conteúdo disponível sem ficar presa em uma animação global,
**para que** eu consiga navegar mesmo quando uma consulta secundária estiver lenta ou indisponível.

## Acceptance Criteria

- [ ] AC1: O bootstrap aguarda a hidratação da sessão local antes de escolher o endpoint público ou privado.
- [ ] AC2: Existe no máximo uma requisição de bootstrap ativa por ciclo de carregamento; requisições obsoletas são canceladas ou ignoradas.
- [ ] AC3: A sessão inválida gera uma única transição controlada para o bootstrap público, sem loop ou duplicação de chamadas.
- [ ] AC4: O bootstrap possui timeout configurável e estados explícitos de carregamento, sucesso, degradação e erro com opção de retry.
- [ ] AC5: O endpoint público não carrega scores e leaderboard globais para a home quando esses dados não são necessários; consultas passam a usar projeções e escopo adequados.
- [ ] AC6: O endpoint privado aplica filtros de papel no servidor e evita retornar dados globais desnecessários para manager e athlete.
- [ ] AC7: Páginas estáticas e o shell da aplicação não ficam bloqueados pelo carregamento completo do Supabase; dados secundários podem carregar progressivamente.
- [ ] AC8: Falhas de consultas são registradas com duração, endpoint, status e contexto suficiente para diagnosticar latência sem expor PII.
- [ ] AC9: Testes cobrem reload anônimo, reload autenticado, sessão expirada, timeout, erro de bootstrap, retry e ausência de requisições duplicadas.

## Dev Notes

- O overlay global é renderizado por `src/components/AppLoadingWrapper.tsx` dentro de `src/app/layout.tsx`.
- A seleção público/privado e o efeito de carregamento estão em `src/context/AppContext.tsx`.
- A persistência local da sessão está em `src/hooks/useLocalStorage.ts`.
- O payload público é montado em `src/lib/bootstrapPayload.ts`; o privado é montado em `src/app/api/app/bootstrap/route.ts`.
- O projeto usa Next.js App Router, React e Supabase server-side; o cliente não deve consultar o Supabase diretamente.
- Manter sanitização de PII e isolamento por papel existentes.
- Não usar dados mock como sucesso silencioso em produção quando o bootstrap falhar.

### Completion Notes

Implementação concluída para revisão. O bootstrap agora aguarda a hidratação da sessão,
coordena uma única requisição ativa com abort/timeout, trata sessão expirada uma única vez,
expõe estados de loading/ready/degraded/error e permite retry. O endpoint público foi reduzido
ao payload necessário para a navegação inicial; atletas, scores e leaderboard são carregados
por evento sob demanda. O endpoint privado usa projeções explícitas e filtros server-side por
papel. O shell deixou de ser bloqueado por overlay de tela inteira e erros de bootstrap ficaram
visíveis e recuperáveis. Logs de duração, status, contexto e tamanho do payload foram adicionados.

Validações executadas: `npm run typecheck`, `npm test` (114 aprovados), `npm run lint` (0 erros,
19 warnings legados) e `npm run build` (sucesso). A validação manual com rede lenta/Supabase
indisponível permanece recomendada em ambiente de homologação.
