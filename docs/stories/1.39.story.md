# Story 1.39 - Endurecimento da Criação de Inscrições

## Status

InReview

## Context

A criação de inscrição em `/api/registrations/start` passa a gerar no servidor o identificador da inscrição, o do atleta novo e a data de criação, que antes eram aceitos do navegador. O servidor passa a ser a única fonte desses valores e a criação passa a ser uma inserção simples, que nunca altera uma inscrição já existente.

Decisões do usuário (14/10/2026): plano em fases aprovado; esta fase (Fase 0) sai **junto** com a Story 1.38 (mesma publicação, migration da 1.38 antes do código); verificação de leitura no banco autorizada e feita.

Story criada pelo orquestrador a partir da decisão explícita do usuário (a aprovação dele substitui a validação do @po).

## User Story

**Como** organizador de eventos,
**quero** que cada inscrição seja criada somente com identificadores e datas gerados pelo servidor,
**para que** cada criação gere sempre um registro novo e o histórico de inscrições seja consistente.

## Acceptance Criteria

- [x] AC1: O servidor gera o identificador da inscrição (`reg-<uuid>`) e o do atleta novo (`ath-<uuid>`) e ignora qualquer `id` enviado pelo navegador em `registrationData` e `athleteProfile`. A inscrição manual da Bilheteria usa o mesmo gerador.
- [x] AC2: A data de criação (`created_at`) é sempre a do servidor; o valor enviado pelo navegador é ignorado.
- [x] AC3: `/api/registrations/start` grava a inscrição com `insert` (nunca `upsert`). Conflito de chave devolve 409 com a mesma mensagem de inscrição ativa já existente, sem alterar nenhuma linha.
- [x] AC4: O fluxo do atleta continua funcionando de ponta a ponta: o navegador usa o `id` e o `accessToken` devolvidos pelo servidor em todas as chamadas seguintes (Pix, cartão, preference, status, e-mail), e o reenvio idêntico continua reaproveitando a resposta guardada (Story 1.38).
- [x] AC5: O preço de uma categoria sem valor definido não pode virar inscrição gratuita: usa o preço padrão do evento e, se ambos estiverem ausentes, a criação é recusada com mensagem clara.
- [x] AC6: Nenhuma rota de pagamento é alterada nesta fase.
- [x] AC7: Testes: unitários do gerador de identificadores; regressão estática (sem `upsert` nem `registrationData.id` na criação); teste de comportamento que prova que uma segunda requisição de criação nunca altera uma inscrição existente. `npm test`, `npm run lint` (0 erros), `npm run typecheck` e `npm run build` passam.

## Dev Agent Record

### Completion Notes

**Entrega.** O servidor passa a gerar `reg-<uuid v4>` para a inscrição e `ath-<uuid v4>` para o atleta novo (módulo puro `registrationIds.ts`), ignora o `id` e o `createdAt` enviados pelo navegador, e grava a inscrição com `insert` (conflito de chave devolve 409 com a mensagem de inscrição ativa, sem alterar linhas). A Bilheteria usa o mesmo gerador. `created_at` é o horário do servidor. Categoria sem preço usa o preço do evento e, sem nenhum dos dois, a criação é recusada (409); preço 0 explícito continua gratuito (`resolveTicketPrice`, usado no snapshot e na validação do cupom). O fluxo do atleta já usava só o `id` e o `accessToken` devolvidos pelo servidor; foi conferido ponto a ponto (Pix, cartão, preference, status, e-mail, `registerTicket`, reenvio idêntico da Story 1.38).

**Verificação.** `node --test tests/*.test.mjs`: 559/559 (com as Stories 1.38 e 1.40 no mesmo tree). `npm run lint`: 0 erros (208 avisos, mesma base). `npm run typecheck`: sem erros. `npm run build`: ok. Teste de mutação: reintroduzir `upsert`, o id/`createdAt` do navegador ou a leitura antiga do preço faz os testes novos falharem. Foi criado um harness de testes (`tests/support/serverModuleHarness.mjs` e `fakeSupabase.mjs`) que roda a rota e o snapshot reais com um banco em memória que reproduz as chaves únicas das migrations; os testes de comportamento provam que uma segunda criação com o mesmo id enviado pelo navegador cria uma inscrição nova com id do servidor e não altera a existente.

**Pendências conhecidas (LOW).** O `users.id` do atleta novo ainda usa `Date.now()` + aleatório (só `insert`, sem efeito sobre inscrições). Quando o `start` devolve 409 ou 400 depois de criar usuário, senha e atleta novo, essas gravações permanecem (ordem anterior mantida; tratar com transação/RPC em fase futura). `ath-${Date.now()}` ainda é usado como reserva de montagem de e-mail em `triggerRegistrationApprovedEmail` e `checkout/email`, sem gravação.
