## Context

Decisão D7 (2026-10-20): o telão detecta pelas súmulas quem está sendo julgado, sem depender do horário do cronograma, porque atrasos são comuns. O cronograma dá a ordem, as raias e os nomes.

Plano aprovado pelo usuário em 2026-10-19 (decisões D1 a D4) e 2026-10-20 (D5 a D9): [docs/PLANO-TELAO-LEADERBOARD-AO-VIVO.md](../PLANO-TELAO-LEADERBOARD-AO-VIVO.md). Desenho aprovado: [docs/design/telao-ao-vivo/](../design/telao-ao-vivo/README.md). A aprovação do usuário substitui a validação do @po, como nas Stories 1.43 a 1.52.

## User Story

**Como** organizador,
**quero** que o telão troque sozinho entre chamada, bateria e geral,
**para** não precisar de uma pessoa operando a TV.

## Acceptance Criteria

- [x] AC1: `GET /api/telao/[token]`: link inválido ou revogado responde 404 ("Link do telão desativado…"). Sem sessão; limite por token e IP; `Cache-Control: no-store`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`; ETag e 304 quando nada mudou.
- [x] AC2: `resolveBroadcast` (modo automático): bateria ao vivo = grupo com súmula em andamento que recebeu registro nos últimos 20 min; intervalo = todas as súmulas enviadas ou encerrada pela mesa, no ar por pelo menos 90 s; chamada = súmulas abertas sem toque, ou chamada liberada no cronograma; senão o geral da última bateria; sem nenhuma, espera.
- [x] AC3: Grupo = súmulas da mesma bateria (`heat_id`) ou, sem bateria, da mesma prova e categoria.
- [x] AC4: Modos fixados: bateria (ao vivo se já começou, senão chamada), geral de uma categoria, espera.
- [x] AC5: Resposta sem e-mail, telefone, id de atleta, de usuário ou de inscrição. Nome por `sanitizeNamePII` e `getTeamDisplayName`.
- [x] AC6: Intervalo: geral de cada categoria da bateria, com até 4 provas (a recém-publicada em destaque), variação de posição contra o geral antes desta bateria e a próxima bateria do cronograma.
- [x] AC7: Testes e gate `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`.
